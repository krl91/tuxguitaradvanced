T002. The cost of a full Wait repaint of the score (research R2)
How: a throwaway timing print around handle.paintControl() inside fillPaintBuffer() of
desktop/TuxGuitar/src/app/tuxguitar/app/view/util/TGBufferedPainterLocked.java, and a throwaway loop of 100 redraws started 15 s after the
first paint, each redraw asked by redrawLater() after the previous paint. Built app (the jar of desktop/TuxGuitar swapped into the .app, then
put back), tests/demo-arcade-morceau.tg, window 1280x800 (score canvas 1057x587), player stopped (running=false at every paint).
The app was started as a second, isolated instance (its own user.home and java.io.tmpdir) so that the owner's open TuxGuitar and its settings
were not touched.
  run 1: 100 repaints, median 3.199 ms, 95th percentile 3.940 ms (min 2.481, max 9.521)
  run 2: 100 repaints, median 3.243 ms, 95th percentile 3.670 ms (min 2.496, max 6.455)
  (a first run with the default window, canvas 977x462, gave about 2.3-2.5 ms per paint: the cost grows with the visible score)
Decision: HOOK NEEDED. The median is above 3 ms in both runs (the 95th percentile stays below 6 ms). T026 adds the overlay-only repaint
(TGBufferedPainterLocked.requestOverlayOnly, TGControl.redrawOverlay).
The print and the loop were removed: git diff desktop/TuxGuitar is empty.

Follow (research R2, "Follow"): FollowPlayback.start() (session/FollowPlayback.java) mutes the practised track with setPlayerOnlyMute and then
calls play() on the application's MidiPlayer (session/MidiFollowPlayer.java), so MidiPlayer.isRunning() is true during a Follow run, backing on
or muted, and TGControl.paintTablature takes its incremental branch (only the played beat, when it changed). This was checked by reading the
source only: starting a Follow run needs the practice window and was not automated, so the print was not seen with running=true. With the
hook added anyway, the score fire asks for the overlay-only repaint in both modes, so the Follow answer does not change the plan.

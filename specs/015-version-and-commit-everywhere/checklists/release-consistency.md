# Release Consistency Checklist: The same version and commit everywhere

**Purpose**: Unit tests for the requirements of spec 015 (and the plan that carries them): are they complete, clear, consistent and measurable before tasks are written. Formal release-gate depth, reviewer audience, focus on (1) the notations of the version per system, (2) the release pipeline and its failure paths, (3) what the application shows.
**Created**: 2026-10-22
**Feature**: [spec.md](../spec.md), [plan.md](../plan.md)

**Review Ownership**: reviewer-owned requirements-quality artifact. `[x]` means the reviewer judged the requirements-quality criterion satisfied; it does NOT mean implementation work is done.

## Notations of the version per system

- [ ] CHK001 Is "identical" defined for places that must use another notation (macOS numeric short version, Windows numeric file version, Debian `~`)? SC-001 says the version read from each place "is the version asked for", FR-009 allows a different notation. [Conflict, Spec §SC-001 vs §FR-009]
- [ ] CHK002 Is the mapping from a free label to the Debian version defined without loss? Plan R8 maps `-` to `.`, so `v0.6.0-beta-1` and `v0.6.0-beta.1` would give the same Debian version. [Ambiguity, Plan R8]
- [ ] CHK003 Is the macOS rule consistent between FR-003 ("state the release version") and the Apple constraint that the short version is numeric, with the full text moved to other fields? Which field must the verifier treat as "the version"? [Consistency, Spec §FR-003, Plan R6]
- [ ] CHK004 Is the Windows requirement conditional on a launch4j capability that has not been confirmed (version resource fields)? Is the fallback stated if the plugin cannot carry the text version? [Assumption, Plan R7]
- [ ] CHK005 Are the limits of a label specified (length, case, leading zeros, a numeric-only label, characters accepted in file names and in the Debian field)? FR-011 says "letters, digits, dots and hyphens" only. [Completeness, Spec §FR-011]
- [ ] CHK006 Is the order of two labelled versions relevant to any requirement (updates, Debian sorting `beta.2` after `beta.1`, `test` before the final)? If not, is that stated? [Gap]

## Pipeline and failure paths

- [ ] CHK007 Is the behaviour defined when the check fails after some packages were already attached to the draft release (the draft stays, is deleted, or is marked)? [Gap, Exception Flow, Spec §FR-006]
- [ ] CHK008 Is the re-run of the same tag after a failed check specified (existing draft, assets already attached, `--clobber`)? [Recovery, Gap]
- [ ] CHK009 Is a tag that already exists on a different commit than the one built a refusal case in the requirements, and which comparison is made (spec §FR-006 says the commit equals the tag's)? [Coverage, Spec §SC-002, Plan R11]
- [ ] CHK010 Is the order of stamping and macOS signing required to be such that the signature is not broken by a later metadata edit? [Gap, Dependency]
- [ ] CHK011 Does FR-006 say which checks run before the first upload versus before publication, given the packages are attached one platform at a time? [Clarity, Spec §FR-006]
- [ ] CHK012 Is it defined what "modified" means for a CI release build (files generated by the build, untracked files), so that a release can never show "modified" by accident? [Ambiguity, Spec §FR-007]
- [ ] CHK013 Are requirements stated for the SWT build variants that are not released (JavaFX, Qt, FreeBSD, the two installer variants), either in scope or explicitly out? [Scope, Gap]
- [ ] CHK014 Is it stated that already published releases (v0.6.0-alpha.1 to beta.1) are not re-stamped? [Assumption, Gap]
- [ ] CHK015 Is the place where the release page states the commit specified (notes footer, title, both) and its exact form, so that it can be read by the verifier? [Clarity, Spec §FR-004]

## What the application shows

- [ ] CHK016 Is the default title requirement reachable for existing users whose configuration already stores the previous default layout (the layout is a stored, editable setting)? [Gap, Assumption, Spec §FR-002, Plan R3]
- [ ] CHK017 Does the spec distinguish "a layout the user wrote" from "the old default stored by the application", and say which one is replaced? [Ambiguity, Spec §FR-002]
- [ ] CHK018 Is the command-line version output (`--version`) a requirement? The plan changes it (R2) but no functional requirement covers it. [Traceability, Gap]
- [ ] CHK019 Is the place of the full commit in the About window fixed (which tab or line) and its legibility measurable? [Clarity, Spec §FR-002, §SC-003]
- [ ] CHK020 Are the feedback and failure of the Copy button specified (confirmation shown, clipboard unavailable)? [Coverage, Exception Flow, Spec §FR-013]
- [ ] CHK021 Is the copied line's language or fixed English form stated (it is pasted into reports)? [Clarity, Spec §FR-013]
- [ ] CHK022 Is the title for a development build defined with the same precision as for a release (`dev` shown instead of the version; commit not in the title)? [Consistency, Spec §FR-007 vs clarification 5]
- [ ] CHK023 Are the other texts that print "the application version" listed (variable description in 26 languages, MusicXML software tag, config file)? Is the choice to leave them as they are stated? [Coverage, Plan R2, R3, Spec §FR-008]
- [ ] CHK024 Is Android (which has its own version variable) explicitly out of scope in the spec, not only in the plan? [Scope, Plan R4]

## Acceptance and measurability

- [ ] CHK025 Can SC-001 ("9 places") be enumerated unambiguously from the spec, with the same list as the plan's verifier table? [Measurability, Spec §SC-001, Contract verify-version]
- [ ] CHK026 Is SC-004 ("one wrong value in any place") bounded to a stated list of places and wrong-value kinds (version, label, commit, short vs full)? [Measurability, Spec §SC-004]
- [ ] CHK027 Is the "release built in the same workflow run" the only supported source of a release, or can a package be rebuilt locally and uploaded (what then is checked)? [Assumption, Spec §FR-001]
- [ ] CHK028 Is every requirement FR-001..FR-013 traceable to at least one acceptance scenario or success criterion (FR-005, FR-010, FR-012 are only indirectly covered)? [Traceability]
- [ ] CHK029 Are the claims about Windows and Linux stated as validated by CI only, so that no requirement is reported as verified without a run? [Assumption, Plan Constitution IX/XII]

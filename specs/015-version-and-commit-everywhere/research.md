# Research: the same version and commit everywhere

Evidence is from the source inspected on 2026-10-22.

- **R1 Today's About**: `TGAboutDialog.RELEASE_NAME = TGApplication.NAME + " " + TGVersion.CURRENT.getVersion()` (line 33), used as the header label (`title.setText(RELEASE_NAME)`). `TGVersion.CURRENT = new TGVersion(2,1,1)` (`common/TuxGuitar-lib/.../util/TGVersion.java:5`); `getVersion()` prints only digits (no label), so it cannot carry `-beta.1`.
- **R2 Other readers of `TGVersion.CURRENT`** (all stay as is): `TGSongWriterImpl:95-97` (`.tg` header), `KeyBindingWriter:85`, `TGConfigManager:39` (`CONFIG_APP_VERSION`), `MusicXMLWriter:129`, `ArgumentParser:62` (`--version` prints `NAME - 2.1.1`). **Decision**: `ArgumentParser` is changed to print the build identity too (it is "the version shown by the application"); the others are file/config formats.
- **R3 `${appversion}`**: `TGVarAppVersion` (name `appversion`) registered in `TGVarAdapter:16`, documented in `MainOption` and in messages (`settings.config.main.window-title.var.description.appversion`). Title is resolved from `TGConfigKeys.WINDOW_TITLE`, default `${appname} - ${filename}`. **Decision**: change the default to `${appname} ${appversion} - ${filename}`; a stored user layout wins untouched. Existing translations of the variable description say "version of TuxGuitar": English/French/Spanish refreshed, others left (no unrelated edits).
- **R4 Android** has its own `TGVarAppVersion` using `TGVersion.CURRENT`: out of scope (the spec concerns the three desktop systems).
- **R5 Where to carry the identity into a package**: a file in `share/` found by the existing `tuxguitar.share.path` (`TGFileUtils:27,177`; set by the launchers: Windows `-Dtuxguitar.share.path=share` in launch4j opts; macOS/Linux scripts likewise). A jar resource was rejected: the jars are built once and shared with local builds; a generated file in the packaged tree is stamped per build without rebuilding.
- **R6 macOS**: `common-macosx/Contents/Info.plist` says `9.99-SNAPSHOT` for `CFBundleShortVersionString`/`CFBundleVersion`; the macOS POM already edits it with `PlistBuddy` exec steps (`Set :CFBundleGetInfoString TuxGuitarAdvanced ${project.version}`). **Decision**: same mechanism with properties; `CFBundleVersion` = `X.Y.Z.0` (clarification 4); `CFBundleShortVersionString` must be numeric on macOS (Apple rule: up to three period-separated integers), so it carries `X.Y.Z` and the full text goes in `CFBundleGetInfoString` and a custom key `TGBuildVersion`/`TGBuildCommit`. (FR-009 says numeric part in numeric fields; the full text in another field of the package.)
- **R7 Windows**: launch4j plugin 2.1.2 config has no `versionInfo` today; it supports `fileVersion` (4 numbers), `txtFileVersion`, `productVersion`, `txtProductVersion`, `fileDescription`, `copyright`, `productName`, `internalName`, `originalFilename`. To confirm by running the Windows build in CI (cannot be run on this macOS machine: the pom needs Mingw cross-compiling).
- **R8 Debian**: control file `Version: 9.99-SNAPSHOT-linux-swt` (`tuxguitar-linux-swt-deb/src/resources/DEBIAN/control`). Debian sorts `0.6.0~beta.1` before `0.6.0`. **Decision**: `Version: X.Y.Z~label` (label punctuation: Debian allows `~ . + alnum`, so a free label with `-` is mapped `-`→`.`); the full text and commit go in the `Description` trailer line; file name keeps the tag.
- **R9 Tests location**: `desktop/TuxGuitar` has `src/` only (CLAUDE.md: tests live in `common/` modules and the fork modules). **Decision**: put `TGBuildInfo` in `desktop/TuxGuitar-practice`? No: that is a plugin and About is core. Open point for task 1: either a `test/` dir for `desktop/TuxGuitar` (pom change) or place the pure class `BuildIdentity` in `common/TuxGuitar-lib` (already tested, release 9, JUnit 5) and keep only the file reading in the app. **Chosen**: pure `BuildIdentity` (parse, formats, short/full, modified, dev label) in `common/TuxGuitar-lib` `app.tuxguitar.util`, new class only; the app reads the file. Justification for a `common/` addition: tests exist there and nothing else carries them; new class, no existing code changed.
- **R10 Workflow today**: `TG_VERSION: '9.99-SNAPSHOT'` is the Maven version of the modules (file names inside `target`), `RELEASE_TAG` the dispatch input; packages are renamed with `${RELEASE_TAG}`; the draft release is created with `--target "$GITHUB_SHA"` and title `TuxGuitarAdvanced $RELEASE_TAG`; the final job publishes the draft and sets `--prerelease` only for `*alpha*|*beta*|*rc*`. **Decision**: keep `TG_VERSION` (changing the Maven version would touch every POM and break the sibling-SNAPSHOT dependency scheme); the *release* version is a separate value passed as properties. Prerelease = tag has a label.
- **R11 Commit**: `GITHUB_SHA` is the checked-out commit; `--target "$GITHUB_SHA"` makes the tag point to it. A tag already existing on another commit is checked at the start (`git ls-remote`-free: `gh release view` / `gh api`), one network call.
- **R12 Dev label**: `git rev-parse HEAD`, `git status --porcelain` at build; no git ⇒ `unknown` (FR-007). Written by the same script as the release path, with `--dev`.
- **R13 Licences**: no dependency added.

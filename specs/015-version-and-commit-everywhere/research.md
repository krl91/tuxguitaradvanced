# Research: the same version and commit everywhere

Evidence is from the source inspected on 2026-10-22.

- **R1 Today's About**: `TGAboutDialog.RELEASE_NAME = TGApplication.NAME + " " + TGVersion.CURRENT.getVersion()` (line 33), used as the header label (`title.setText(RELEASE_NAME)`). `TGVersion.CURRENT = new TGVersion(2,1,1)` (`common/TuxGuitar-lib/.../util/TGVersion.java:5`); `getVersion()` prints only digits (no label), so it cannot carry `-beta.1`.
- **R2 Other readers of `TGVersion.CURRENT`** (all stay as is): `TGSongWriterImpl:95-97` (`.tg` header), `KeyBindingWriter:85`, `TGConfigManager:39` (`CONFIG_APP_VERSION`), `MusicXMLWriter:129`, `ArgumentParser:62` (`--version` prints `NAME - 2.1.1`). **Decision**: `ArgumentParser` is changed to print the build identity too (it is "the version shown by the application"); the others are file/config formats.
- **R3 `${appversion}`**: `TGVarAppVersion` (name `appversion`) registered in `TGVarAdapter:16`, documented in `MainOption` and in messages (`settings.config.main.window-title.var.description.appversion`). Title is resolved from `TGConfigKeys.WINDOW_TITLE`, default `${appname} - ${filename}`. **Decision**: change the default to `${appname} ${appversion} - ${filename}`; a stored user layout wins untouched. Existing translations of the variable description say "version of TuxGuitar": English/French/Spanish refreshed, others left (no unrelated edits).
- **R4 Android** has its own `TGVarAppVersion` using `TGVersion.CURRENT`: out of scope (the spec concerns the three desktop systems).
- **R5 Where to carry the identity into a package**: a file in `share/` found by the existing `tuxguitar.share.path` (`TGFileUtils:27,177`; set by the launchers: Windows `-Dtuxguitar.share.path=share` in launch4j opts; macOS/Linux scripts likewise). A jar resource was rejected: the jars are built once and shared with local builds; a generated file in the packaged tree is stamped per build without rebuilding.
- **R6 macOS**: `common-macosx/Contents/Info.plist` says `9.99-SNAPSHOT` for `CFBundleShortVersionString`/`CFBundleVersion`; the macOS POM already edits it with `PlistBuddy` exec steps (`Set :CFBundleGetInfoString TuxGuitarAdvanced ${project.version}`). **Decision**: same mechanism with properties; `CFBundleVersion` = `X.Y.Z.0` (clarification 4); `CFBundleShortVersionString` must be numeric on macOS (Apple rule: up to three period-separated integers), so it carries `X.Y.Z` and the full text goes in `CFBundleGetInfoString` and a custom key `TGBuildVersion`/`TGBuildCommit`. (FR-009 says numeric part in numeric fields; the full text in another field of the package.)
- **R7 Windows** (confirmed 2026-10-22 by reading `launch4j-maven-plugin` 2.1.2 and its dependency `net.sf.launch4j:launch4j:3.14`, class `net.sf.launch4j.config.VersionInfo`): `versionInfo` has `fileVersion`, `txtFileVersion`, `fileDescription`, `copyright`, `productVersion`, `txtProductVersion`, `productName`, `companyName`, `internalName`, `originalFilename`, `trademarks`. `fileVersion` and `productVersion` are four numbers (`VERSION_PATTERN`), the `txt…` ones are free text, so the full release text (`0.6.0-beta.1`) fits in `txtFileVersion` and `txtProductVersion`. The exe itself is built only in CI (Mingw cross-compile); not run here.
- **R7b Reading the Windows version in CI** (decision): `strings -e l tuxguitar.exe` (binutils, present on the Ubuntu runner and on macOS) prints the UTF-16LE version-resource strings; the verifier looks for the lines `FileVersion`, `ProductVersion` followed by their value. No new dependency. `exiftool` exists on this Mac but not on the runner, `pefile` is not installed here; they are not used. The self-test builds a fake exe holding UTF-16LE resource strings; the reading of a **real** launch4j exe is only proved by CI.
- **R8 Debian**: control file `Version: 9.99-SNAPSHOT-linux-swt` (`tuxguitar-linux-swt-deb/src/resources/DEBIAN/control`). Debian sorts `0.6.0~beta.1` before `0.6.0`. **Decision**: `Version: X.Y.Z~label` (label punctuation: Debian allows `~ . + alnum`, so a free label with `-` is mapped `-`→`.`); the full text and commit go in the `Description` trailer line; file name keeps the tag.
- **R9 Tests location** (revised after the analysis): `desktop/TuxGuitar` has no test directory, but `desktop/TuxGuitar-practice/test/` already tests classes of the `tuxguitar` module (`PreRunWindowLevelSwtTest`; the practice module depends on `tuxguitar`). **Decision**: `BuildIdentity` (pure: parse, formats, validation) and `TitleLayoutDefault` (pure) go in `desktop/TuxGuitar`, package `app.tuxguitar.app.system`, and are tested from the practice module's tests; `common/` is not modified (constitution II). Task T004 confirms the dependency before any code; if it fails, the owner decides between a test directory for `desktop/TuxGuitar` and a justified addition in `common/TuxGuitar-lib`. **Confirmed 2026-10-22**: `desktop/TuxGuitar-practice/pom.xml` declares `tuxguitar` with scope `provided`, which is on the test classpath, and existing practice tests already use `app.tuxguitar.app.*` classes. The title is resolved by `TGExpressionResolver` (`common/TuxGuitar-lib`, `resolve(String)` with `MapPropertyResolver`), which needs no window: `TGWindow.loadTitleInCurrentThread` only calls `TGExpressionResolver.getInstance(context).resolve(layout)`. So the wiring test can resolve a layout with the real `TGVarAppVersion` registered in a map, without a window.
- **R10 Workflow today**: `TG_VERSION: '9.99-SNAPSHOT'` is the Maven version of the modules (file names inside `target`), `RELEASE_TAG` the dispatch input; packages are renamed with `${RELEASE_TAG}`; the draft release is created with `--target "$GITHUB_SHA"` and title `TuxGuitarAdvanced $RELEASE_TAG`; the final job publishes the draft and sets `--prerelease` only for `*alpha*|*beta*|*rc*`. **Decision**: keep `TG_VERSION` (changing the Maven version would touch every POM and break the sibling-SNAPSHOT dependency scheme); the *release* version is a separate value passed as properties. Prerelease = tag has a label.
- **R11 Commit and tag**: `GITHUB_SHA` is the checked-out commit; the draft is created with `--target "$GITHUB_SHA"`. A **draft release has no git tag until it is published** (to be confirmed by the experiment of task T005). So before publication the check compares the draft's **target commit**, and right after publication it reads the **tag** and compares it with the commit; the validate job refuses a tag name that already exists as a git tag on another commit or whose release is published.
- **R12 Dev label**: `git rev-parse HEAD`, `git status --porcelain` at build; no git ⇒ `unknown` (FR-007). Written by the same script as the release path, with `--dev`.
- **R13 Licences**: no dependency added.
- **R14 System clipboard** (found while implementing T019, 2026-10-22): `grep -ril clipboard` in `desktop/TuxGuitar-ui-toolkit*/src` finds nothing; the only `TGClipboard` (`common/TuxGuitar-editor-utils`) is the in-application copy of song data, not the system one. **Decision**: the smallest addition is a separate interface `UITextClipboard { boolean copyText(String) }` in `TuxGuitar-ui-toolkit`, implemented by `SWTFactory` (SWT `Clipboard` + `TextTransfer`, validated on macOS). `UIFactory` is not changed; JavaFX and Qt do not implement it and About then says the copy is not available and keeps the line selectable. `java.awt` was rejected (starting AWT beside SWT on macOS is unsafe), and shell commands (`pbcopy`, `clip`, `xclip`) were rejected (not available everywhere). Constitution II: justified by this inspected absence.
- **R11b Probe of a draft release (task T005, run 2026-10-22 on `krl91/tuxguitaradvanced` with the owner's go)**: `gh release create zz-probe-015 --draft --target <sha>` created a draft (URL `releases/tag/untagged-…`). `gh release view --json tagName,targetCommitish,isDraft,name` returned `tagName=zz-probe-015`, `targetCommitish=<the full sha given>`, `isDraft=true`; `GET repos/<repo>/git/ref/tags/zz-probe-015` returned **404: a draft has no git tag**. The draft was deleted and the 404 and the empty listing were checked afterwards. **Confirms** the plan: before publication the check compares `targetCommitish`; the git tag is read right after publication. **Warning found**: in this working copy `gh repo view` resolves to the **upstream** repository (`helge17/tuxguitar`), not the fork: every local `gh` command must pass `--repo krl91/tuxguitaradvanced` (the first attempt of the probe went to upstream by mistake, failed with 404 for lack of rights, and created nothing there: checked). In the workflow `--repo "$GITHUB_REPOSITORY"` is used.

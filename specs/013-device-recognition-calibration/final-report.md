# Final report, spec 013 "per-device calibration of note and chord recognition"

Written 2026-10-16, branch `feature/interactive-practice`, local commits only (nothing pushed).

## What was built (phases 1 to 6, T001 to T044)
- **Model and store**: `DeviceKey`, `RecognitionProfile`, `RecognitionRate`, `FrontEndState`, `ProfileState`; the settings store has a default layer and an effective `get()` (default plus the active profile for 11 profile parameters); the real writers (Configuration page, `FollowSettings.setWindowMillis`) write the default layer.
- **Library** of profiles in its own module `tuxguitar-recognition-profiles` (unreadable entries skipped and kept, a failed write keeps the old profile, `remove`, listeners).
- **Scoring and search**: `SoundSegmenter`, `EventJudge` (copy of the test judge, same verdicts on the 21 notes), `CalibrationScorer` (right minus 2 per wrong acceptance against the next event), `ProfileSearch` (deterministic coordinate descent from the default, one point of gain to leave it, budget 120 s / 2000 candidates, cancel).
- **Listening mode**: `HopRecorder` (memory only), `SoundCounter`, `RecordingQuality`; `NoAudioOnDiskSourceTest` forbids any file API in the calibration code.
- **Flow, controller, window**: `CalibrationFlow` (pure table), `CalibrationController`, `CalibrationWindow` (one modal window; closing asks "Stop the calibration?"), 67 texts in English, French and Spanish.
- **Activation and dot**: `ProfileActivator` (attached in `AudioEngine.getInstance`), `EngineListeningPort`, `ProfileDot` (grey / orange / green / red, warning, Calibrate, Forget with confirmation), `CalibrationLauncher`, opt-in in `InputSelectorPanel` (Configuration page unchanged), one line in `PracticeWindow`.
- **Documentation** (T045): a new section in the three help pages, `docs/PRACTICE.md`, `README.md`, `specs/STATUS.md`.

## What ran
- Whole default suite after a clean compile with `mvn -e clean verify -P native-modules`: see `benchmark/baseline.txt` (practice 1044 tests, 6 skipped; engine 373; 0 failures) and the last run of phase 7 below.
- Native tests with `-P swt-gui-tests`: `ProfileDotSwtTest`, `PracticeWindowSwtTest`, `RecognitionSettingsSwtTest`, green on this Mac.
- No existing test was modified, renamed or deleted. The recognition code (`analysis`, `recognition`, `pitch`) is byte-identical to the base `1f385c40d`; the recognition reports regenerated by the suite left `git status` clean.

## What was skipped or not covered
- **T004, T046 (the real measure)**: the owner's recording of `basic_test.tg` does not exist, so the search has never run on real data. **There is no measured gain for the built-in microphone.** On a synthetic performance the search kept the default (nothing to gain). See `benchmark/validation.txt` for the exact command once the take exists.
- **T049, T050 (owner's trial, the one window)**: human tasks, open.
- `InputSelectorPanel` as a whole is not built by any test (it needs the real input catalog); `ProfileDot` is tested headless and natively, the panel's opt-in on the source.
- No "tab shown" refresh of the dot (only one line of `PracticeWindow` could change) and a gain change is not announced by the engine, so the gain warning can be stale until the next refresh.
- Known limit of the existing recognition, out of scope: a chord with a note missing is often accepted, so the chord score can count a partly played chord as recognised.

## Defects found by the tests and fixed in the code
A clipped take reported as a silence timeout; the search unable to walk far from the default; the highest level starting at 0 dBFS; a recording asked before the rate was announced was reset; the lead before a segment too short. Defects in my own new tests (a wait on an unread ring buffer, string comparison of proxy colours) were fixed in those tests.

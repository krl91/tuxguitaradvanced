# Research: per-device calibration of the recognition (spec 013)

Every claim cites a file opened on 2026-10-15. `AE` = `desktop/TuxGuitar-audio-engine/src/main/java/app/tuxguitar/audio/engine`, `AET` = `desktop/TuxGuitar-audio-engine/src/test/java/app/tuxguitar/audio/engine`, `PR` = `desktop/TuxGuitar-practice/src/app/tuxguitar/app/tools/custom/practice`, `PT` = `desktop/TuxGuitar-practice/test/app/tuxguitar/app/tools/custom/practice`.

## R1 - Where "profile of the device, else the default" is chosen (FR-007, FR-010)

**Evidence.** The settings are read through `RecognitionSettingsStore.get()` at about twelve production sites: `PracticeWindow` (l.686, 785, 1000 when a session is built), `EngineFollowAdapter`, `FollowSettings`, `PassageSettings`, `AudioEngine` (`settingsChanged` applies the front end and rebuilds the analysis when an engine value changed), `TunerWindow`, `AudioRecognitionOption`, `EngineGainBackend`. `RecognitionSettings` is immutable with `with(parameter, value)`, `fromStrings` and `toStrings`. The Configuration window (`PR/ui/RecognitionSettingsPanel`) edits a pending copy and writes it with `store.update`. **Writers** exist too: `FollowSettings.setWindowMillis` (spec 012) does `store.update(store.get().with(...))`.

**Decision.** The store gets a second layer: `getDefault()` (what the Configuration window edits and what is saved today) and `get()` = the **effective settings**: the default **merged with the active profile**, the profile holding values only for the *profile parameters* (R2). `setActiveProfile(profile-or-null)` is the single place the choice is made; the readers keep calling `get()` and **receive the effective settings without any change**; `AudioEngine.settingsChanged` already rebuilds the analysis when the engine values differ, so a profile applies to the running engine: `AudioEngine.engineValuesDiffer` (l.384) compares `INPUT_LEVEL_MIN`, `INPUT_LEVEL_MAX`, the clip values, `NOTE_ATTACK`, `ATTACK_MIN_LEVEL` and `ENGINE_PITCH`, so a profile that changes a level or attack value rebuilds the analysis once, as an input change does. **Who activates the profile:** not `InputSelectorPanel`, which exists only while the preparation window is open (the tuner window and the practice readers use the engine without it). A small `ProfileActivator` (engine package `calibration`) listens to `CurrentInputSelection` (the engine does the same, `AudioEngine` l.94) and calls `setActiveProfile` for the selected device and the capture rate; it is created with the engine singleton (`AudioEngine.getInstance`, one declared line) and also at start for the remembered input. **The profile applies everywhere the input is used** (spec 2026-10-15: tuner window, Follow, Arcade, Wait) because they read the same store; the tuner's own parameters (`TUNER_IN_TUNE`, `TUNER_HOLD`, `TUNER_CONFIDENCE`) are not profile parameters. A change of input during an exercise has **no special handling** (spec). **Every writer must use `getDefault()`**. Checked by grep on 2026-10-15, the production writers are exactly: `AudioRecognitionOption` (l.73 builds the Configuration page from `store.get()`, l.120 `commit` calls `store.update(pending)`, l.124 `restoreDefaults()`), `FollowSettings` l.154 (`store.update(store.get().with(TEMPO_WINDOW, ...))`) and the store's own two `restoreDefaults` (they start from the default layer). `PassageSettings`, `EngineGainBackend`, `EnginePreRunSource`, `EngineFollowAdapter`, `PracticeWindow`, `TunerWindow` and `TunerRecognition` only **read**. Otherwise a write would copy the profile's values into the default. An invariant test: with a profile active, writing any non-profile setting leaves the default's profile parameters untouched.

**Alternatives.** Making every reader ask a profile manager (rejected: twelve sites, easy to miss one). A separate settings object for the engine (rejected: two sources of truth).

## R2 - What a profile may hold (FR-016, spec Assumptions)

**Evidence.** `AE/settings/RecognitionParameters.java` `ALL` lists: INPUT (level min/max, noise reduction, gain suggestion), TUNER (in tune, hold, confidence), NOTES (accept, fret sharp, confidence, stability, attack, legato, technique, **timing window**), CHORDS (evidence, window, completeness, foreign, min partials, confirm), PASSAGES, ENGINE (pitch engine), ADVANCED (level clip, attack min level). `PracticeParameters.of(settings)` turns the note and chord ones into the `NoteInterpreter`, `TolerancePolicy` and `ChordMatcher` parameters. `PolyphonicAcceptance.Parameters.defaults()` is **not** a recognition setting (code constants).

**Decision.** The **profile parameters** are: `NOTE_ACCEPT`, `NOTE_FRET_SHARP`, `NOTE_CONFIDENCE`, `NOTE_STABILITY`, `NOTE_ATTACK`, `CHORD_EVIDENCE`, `CHORD_WINDOW`, `CHORD_MIN_PARTIALS`, `CHORD_CONFIRM`, `ATTACK_MIN_LEVEL`, `INPUT_LEVEL_MIN`. **Never in a profile:** `ENGINE_PITCH` (the owner's constraint: no algorithm change), the tuner settings, `NOTE_LEGATO` and `NOTE_TECHNIQUE` and `CHORD_COMPLETENESS`/`CHORD_FOREIGN` (choices with one value or a policy of the learner), the passages, the **timing window**, the flames, the gain and the noise-reduction flag (the front end must stay neutral during the calibration, R4). `PolyphonicAcceptance.Parameters` stay code constants: **out of this feature** (declared; a later spec may expose them). Bounds are the existing `Number` minimum and maximum of each parameter.

## R3 - The library and its persistence (FR-007, FR-012, FR-013)

**Evidence.** `RecognitionSettingsStore.ConfigPersistence` (l.117-150) reads and **rewrites its whole file** (`config.clear()` then `save()`), with `MODULE = "tuxguitar-audio-recognition"`, and "keys of other versions are dropped".

**Decision.** The library is **its own file**: a second `TGConfigManager` module, `tuxguitar-recognition-profiles`, behind a small `ProfilePersistence` interface (read and write a map of strings, like `RecognitionSettingsStore.Persistence`) so that tests use an in-memory one. One profile = the keys `profile.<deviceKey>.<parameter key>` plus `profile.<deviceKey>.meta.*` (the date, the sample rate, the rates measured, the rate of the default on the same recording, the layout version); a corrupt or unreadable entry is skipped (that device is orange), never an error (FR-013); saving writes **the whole library** (it is its own file, so nothing else is lost). A cancelled or failed calibration never writes (FR-012): the library is written only by `ProfileLibrary.save(profile)` at the end of a finished choice.

**The key of a profile.** `AudioInputDescriptor` has `getId()`, `getDeviceName()`, `getChannelIndex()`, `getChannelCount()`, `getKind()` (`AE/input/AudioInputDescriptor.java`). **Verified by T003 on 2026-10-15:** `AudioInputDescriptor.getId()` is built by `InputDeviceCatalog.id(...)` as `mixerIndex + ":" + mixerName + ":" + ("mono" | channelIndex)` (`AE/input/InputDeviceCatalog.java` line 118): two identical adapters **do** get different ids at one moment (different `mixerIndex`), **but `mixerIndex` is the position in the system's list of mixers and may change with the plug order or between sessions**, so a key built on the id could give one device's profile to another after a re-plug, or lose it. **Decision (replaces `id#channelIndex`):** `deviceKey = deviceName + "#" + ("mono" | channelIndex) + "#" + ordinal`, where `ordinal` is the rank (0, 1, ...) of the input among the catalog's inputs that have **the same name and channel**, in catalog order; it is 0 for the usual single device. Two identical adapters thus have two keys at a given time (SC-008); if their plug order swaps, they may swap profiles, which is inherent without a hardware serial number and is declared. The activator reads the list from `AudioEngine.getCatalog().listInputs()`. Old decision, kept for the record: `deviceKey = id + "#" + channelIndex`; the sample rate is stored **in** the profile and the profile applies only when the capture rate equals it or is not yet known (a profile made at 48 kHz is not applied at 44.1 kHz: that device then shows orange with the reason). **To verify in the first task:** that `getId()` is unique for two identical adapters on the machine (list the ids of the devices present); if it is not, the key gets the position of the device in the catalog and this is declared (SC-008).

## R4 - Recording the sound and detecting that "a sound was played" (FR-004, FR-017)

**Evidence.** `AE/input/SampleRingBuffer` is read destructively by the analysis and `AudioEngine.getRingBuffer()` is package-private, so it is not a place to tap. The **hop listener of spec 010** (`AnalysisService.addHopListener`, `AudioEngine.addHopListener`) gives every contiguous hop of 256 samples, **after the front end**, on the analysis thread, with `configure(sampleRate)` first: exactly the signal the analysis sees. `OfflineAnalysis` has **no front end** (its javadoc: "the hops are the samples as given"). `AnalysisFrame` has `isOnset()`, `getRmsDbfs()`, `getPeakDbfs()`, `getClippedRatio()`, `getLevelState()`.

**Front-end state (T003):** the gain is read with `AudioEngine.getInputGain()` and the noise reduction with `AudioEngine.isNoiseReductionEnabled()`, both public; the hops given to a `HopListener` are after the front end and `OfflineAnalysis.analyze` does not apply it again (read in `AnalysisService`/`OfflineAnalysis`). **Decision.** A `HopRecorder` (a `HopListener`) copies each hop into a **preallocated** array (no allocation per hop on the analysis thread, constitution VI; capacity 120 s at the rate given by `configure`, then it stops recording and says so). The hops are delivered **after the front end** (`HopListener` javadoc) and `OfflineAnalysis.analyze` does not apply it again, so the recording is exactly the signal live recognition sees: **nothing is refused**; the front-end state at recording time (gain, noise reduction) is read and **stored in the profile** and shown, not enforced. A `SoundCounter` (pure, tested on synthetic signals; `HopListener` gives samples only, so it runs **its own** `ArticulationDetector` and `LevelAnalyzer` on the hops, without allocation) counts a **sound** at each onset whose level is above the input minimum, with a refractory time of 250 ms, **without saying which note or chord**; the mode stops by itself one second after the count reaches the number of events of the piece, ends on a timeout (no sound for 20 s, or 3 minutes in all) and on cancel, each with a reason. **Display bands for the background noise** (starting values, adjustable after the owner's trial, for the word shown at the quality question only; they never refuse a recording): calm below -60 dBFS, medium from -60 to -45 dBFS, loud above -45 dBFS. **The recording stays in memory**: no file is ever written, so FR-017 (deleted after the analysis, on cancel and on failure) holds by construction and is stricter than the owner's answer; the array is dropped when the calibration ends.

## R5 - Scoring a candidate (FR-006, the recognition rate)

**Evidence.** The test module has the judge: `PT/dataset/DatasetJudge.accepts(audio, expected)` builds a one-step practice, feeds the audio after half a second of silence through `OfflineAnalysis.analyze` with `RecognitionSettings.defaults()` and a Wait-mode `PracticeSession` built from `PracticeParameters.of(defaults)` and `PolyphonicAcceptance`, and says whether the step is accepted; `acceptedSteps` and `acceptanceTimes` do the same for a sequence in order.

**Decision.** The scoring is **copied** into production as `EventJudge` (practice module; `DatasetJudge` in the test module is not edited, owner's rule on existing tests): the same procedure with the **candidate settings** used for **both** `OfflineAnalysis` and `PracticeParameters`. The recording is **cut into one segment per sound** at the onsets found while listening (fixed thresholds, independent of the candidate), and each segment is judged **alone against its own event** (a note or a chord of the piece): the result is a boolean per event, independent of earlier misses (the Wait-mode "stuck on the first miss" of a whole-stream judge would hide everything after it). The **rate** is `accepted events / events`, with the notes and the chords also counted separately; the 60 % of the spec is on the total. If the segments do not number the events of the piece the recording is refused (the listening mode already ends on that count).

**A negative control** guards against a candidate that accepts everything: each segment is also judged against the **next event of the piece** (a wrong expectation); the objective is `correct acceptances - 2 x wrong acceptances`, so a loose setting that accepts a wrong note loses more than it gains.

**Cost.** One candidate is about 2 x N one-event offline analyses of about 3 s each (N about 13): measured in the first task; the plan's budget is **120 seconds and 2000 candidates at most**, with a progress figure and a cancel.

## R6 - The search (FR-006, FR-014)

**Decision.** A **deterministic coordinate descent**: start from the default (always the first candidate, so the result is never worse than the default on the recording: FR-014); for each profile parameter in a fixed order, try five values spread over a window of its bounds around the current value, keep the best by the objective (ties: the value nearest the default, a regularisation against overfitting a 13-event recording); repeat passes until a pass improves nothing or the budget ends. Same recording gives the same profile (determinism, constitution VIII, explainable: the report lists each parameter, its default, its new value and what it changed). **Leaving the default requires a gain of at least one event** on the total; otherwise the default is the answer.

**Risk, stated.** 13 events can be over-fitted. The check that matters is **independent**: the built-in-microphone corpus of single notes (R9) and, for chords, the owner's takes, judged with the profile and with the default in the validation phase; **no improvement is promised** (constitution XII), the result is reported.

**Alternatives.** A grid over all parameters (rejected: combinatorial). Random search (rejected: not explainable, seed-dependent). A learned model (rejected by constitution VIII and by the spec).

## R7 - The flow and the windows (FR-001 to FR-005, FR-009, FR-014)

**Evidence.** `PR/ui/PreRunCheck.java` is a pure state machine and `PreRunWindow.java` a window with the tuning question (yes, no-open-the-tuner through `PracticeTunerOpener`) and the strum part; `InputSelectorPanel.java` builds the drop-down, Refresh and "Remember as default" in a `UITableLayout`.

**Decision.** A pure `CalibrationFlow` state machine (like `PreRunCheck`: a total table of states and events, ignored pairs change nothing): `OFFER`, `TUNING`, `TUNER_OPEN`, `ADVICE`, `PIECE`, `LISTENING`, `QUALITY`, `REFUSED`, `ANALYSING`, `RESULT`, `CHOICE`, `DONE`, `CANCELLED`. One **`CalibrationWindow`** whose content changes per step (**decided by the owner on 2026-10-15, to be tried**; each step is its own view class so that separate windows stay a cheap fallback). The window is **modal** during `ANALYSING` (progress bar, *Cancel*; closing it asks "Stop the calibration?" and only a *Yes* cancels the search). The quality question shows **measures** (sounds heard of expected, highest level, background noise, clipping) and has **no replay**. Every refusal (`REFUSED`: wrong number of sounds with the numbers, silent, clipped, timeout, *No* at the quality question) offers *record again*, *use the default configuration* and *stop*, and **no analysis is tried** on a wrong count. The result screen shows the rates **with the default and with the profile**, in total and for the notes and the chords, and "saved for this device". The tuning question reuses the **texts** `practice.prerun.tuned.*` and `PracticeTunerOpener`. The piece is shown as a **list of its events** (note names with string and fret, chords by their notes), with "3 of 13" while listening. The button "Calibrate the recognition" is in the Input tab; **every** device (calibrated, red or never calibrated) first gets the offer **Calibrate / Calibrate again** or **Use the default configuration** (FR-009, clarified). A second button, **Forget the calibration** (FR-019), enabled only for a device with a profile, deletes it after a yes/no confirmation (`ProfileLibrary.remove`). The "not better than the default" message (FR-014) is the `RESULT` step with its three choices.

## R8 - The dot (FR-008, SC-003)

**Decision.** A `ProfileDot` next to the drop-down: a coloured "●" label (`UILabel` foreground colour) **and a short text** ("Calibrated", "Not calibrated: default settings", "Calibrated, recognition 52 %") so that the state is not given by colour alone. It is recomputed from `ProfileLibrary` and the active profile **at every selection change** (`CurrentInputSelection.Listener`, already used by the panel) and after a calibration. The texts are "No input selected", "Not calibrated: default settings", "Calibrated, N %" and "Calibrated, N %, under the 60 % mark" (keys `practice.profile.*`); the dot and the warning are recomputed at every change of input, when the Input tab is shown and when the noise-reduction setting changes (a listener on the recognition store). The rule is a pure function `ProfileState.of(profile, rate)` (no input: **grey `NONE`**, text "No input selected", the *Calibrate* and *Forget* buttons disabled; no profile or a profile chosen as "default" or a profile that does not apply at the current sample rate: orange, with the reason for the rate; profile with total rate >= 60 %: green; profile kept with total rate < 60 %: red), tested on its own. If the **noise reduction or the gain** now differs from what the profile stored, the colour is kept and a **warning sentence** is shown next to the dot; the profile stays in use.

## R11 - Risks found by reading

1. **Writers of the store** must use `getDefault()` (R1): a missed one would silently copy a profile into the default. Mitigation: one invariant test and a grep task listing every `update(` caller.
2. **The profile is applied from a selection event on another thread**: `CurrentInputSelection.notifyListeners` starts **a new thread per notification** (`TGThreadManager.start`), so two quick selections A then B may arrive out of order. The `ProfileActivator` therefore **ignores the content of the event**: under one lock it reads `selection.snapshot()` (the latest revision), looks up that device's profile and calls `setActiveProfile`; the last application always matches the latest selection. It triggers the engine rebuild once (the engine's `settingsChanged` already compares engine values).
3. **Front-end state** (R4): read at recording time and stored in the profile; verified 2026-10-15 that the hops are after the front end and that `OfflineAnalysis` does not repeat it.
4. **Overfitting** on one short recording (R6): guarded by the one-event rule, the regularisation, the negative control and the independent validation; reported honestly.
5. **A device id that is not unique** (R3): verified first.
6. **Time:** a long analysis blocks nothing (a worker thread, progress, cancel) and ends by itself at its budget.
7. **Corpus access** (R9): the 22 notes are in the audio-engine *test* resources; the practice tests reach them through the engine's test-jar (as `FakeAudioInput` is reached); checked in the first phase.
8. **Forgetting a profile** is a deletion: it asks for a confirmation and touches only that device's key.
9. **Activation at start:** the remembered input is selected before any window opens; `ProfileActivator` must therefore also read the current selection when it is created, or the first session would run on the default.
10. **Existing tests must stay unchanged** (owner's rule). Read in the source on 2026-10-15: `PracticeHostSourceTest` counts `AudioEngine.getInstance(` and `new Thread(` in `PracticeWindow.java` and `AppPracticeHost.java` (so neither is edited); `PreRunParityTest` forbids `HopListener`, `StrumClipMeter`, `PreRunCheck` in `arcade/core`, `PracticeSession.java` and the engine's `pitch` and `recognition` directories (so the new engine code is in `calibration` only and those are not edited); `AudioEngineTest` and `RecognitionSettingsPanelTest` call `AudioEngine.getInstance`, which will now create the activator: it reads the library the way the store reads its file, so the test contexts behave as before. `InputSelectorPanel` is built in two places (`PracticeWindow` line 389 for the Input tab and `AudioRecognitionOption` line 79 for the Configuration page), so the calibration controls are **opt-in** through a second constructor and the Configuration page keeps the panel as it is. Read the same day: the native `PracticeWindowSwtTest` walks every visible control of the preparation window (non-zero size, inside the client area), so the new controls go on their own row and the window is refitted; the language tests enumerate the prefixes `practice.follow.`, `practice.mode`, `arcade.`, `practice.prerun.` and `recognition.`, so the new texts use `practice.profile.`; `RecognitionControlsTest` finds help rows by `<tr><td>name</td>` and titles by `<h2>`, and `BrandingAssetsTest` requires the logo path in the markdown surfaces; "calibration" already means the latency calibration of the route (`CalibrationRun`, `CalibrationTaps`, `RouteCalibrationStore`, `practice.follow.calibration.*`), no class name collides but the UI says "Calibrate the recognition"; the activator reads the library like the store reads its file. A gate in every phase checks that no existing test file is modified, and an existing test that fails because of our change is a defect of the change, never of the test.
